> English version: [SQLBraid Dev Notes 1: Why I Built a SQL-First Toolkit for TypeScript](/blog/2026-10-06-sqlbraid-1-why-sql-first-en/)

[SQLBraid](https://github.com/Clickin/SQLBraid)는 TypeScript에서 SQL을 직접 쓰기 위한 데이터 접근 도구입니다. 쿼리는 SQL로 작성하고, SQLBraid는 그 SQL에 들어가는 값을 바인딩 파라미터로 분리하고, 조건에 따라 SQL 일부를 넣거나 빼고, 결과 행을 필요하면 검증합니다. ORM도 쿼리 빌더도 아닙니다.

```ts
import pg from "pg";
import { createPgPoolDatabase, sql } from "sqlbraid/pg";

interface UserRow {
  id: string;
  name: string;
}

const pool = new pg.Pool({ connectionString: process.env.DATABASE_URL });
const db = createPgPoolDatabase(pool);

const userId = 1;
const users = await db.all(sql.rows<UserRow>`
  SELECT id, name FROM users WHERE id = ${userId}
`);
```

이 글은 v1.0.2 기준입니다. 첫 편에서는 왜 SQL을 감추지 않는 쪽을 골랐는지, 그리고 그 대신 라이브러리가 어떤 일을 맡는지 설명합니다. [두 번째 글](/blog/2026-10-06-sqlbraid-2-execution-path/)에서는 쿼리 하나가 값 바인딩부터 연결 반납까지 거치는 경로를 따라갑니다.

## MyBatis에서 출발했다

저는 Java 백엔드를 오래 개발했고, 그 기간 대부분 [MyBatis](https://mybatis.org/mybatis-3/dynamic-sql.html)로 SQL을 썼습니다. MyBatis의 장점은 단순합니다. SQL은 SQL로 남고, 프레임워크는 값을 `#{}`로 바인딩하고, `<if>`, `<where>`, `<set>` 같은 태그로 조건부 SQL을 조립합니다. DBA가 쿼리를 읽을 수 있고, 실행 계획을 확인하려면 SQL을 그대로 복사하면 됩니다.

TypeScript로 넘어오니 선택지는 대체로 두 갈래였습니다.

- ORM은 테이블을 객체로 모델링하고 SQL 생성을 맡습니다.
- [Kysely](https://github.com/kysely-org/kysely) 같은 쿼리 빌더는 SQL 구조를 TypeScript 메서드 체인으로 옮겨 타입 안전성을 얻습니다.

둘 다 좋은 도구입니다. 다만 이미 SQL로 생각하고 있는 사람에게는 번역 단계가 하나 생깁니다. 머릿속의 SQL을 메서드 체인으로 옮기고, 생성된 SQL이 의도와 같은지 다시 확인합니다. 데이터베이스 고유 문법을 쓰려면 결국 raw SQL 탈출구로 나갑니다.

처음 SQLBraid의 목표는 "TypeScript용 MyBatis 동적 SQL"이었습니다. 만들어 가면서 범위를 다시 정했습니다. SQL을 소유하는 프레임워크가 아니라, SQL과 값과 연결을 묶어 주는 바인더(binder)에 가까운 도구가 되어야 한다고 판단했습니다. 그래서 SQLBraid가 맡는 일은 다음 세 가지로 좁혀졌습니다.

1. SQL 구조와 값을 분리해서 바인딩한다.
2. SQL 문법을 깨지 않는 방식으로 조건부 SQL을 표현한다.
3. 연결, 트랜잭션, 스트림 같은 물리적 자원의 수명을 책임진다.

세 번째는 두 번째 글의 주제입니다. 이 글에서는 앞의 두 가지를 봅니다.

## 보간은 언제나 값이다

SQLBraid의 가장 중요한 규칙은 `${...}` 보간이 항상 바인딩 파라미터가 된다는 것입니다. 값은 SQL 문자열에 이어 붙지 않습니다.

```ts
const name = "'; DROP TABLE users; --";
const query = sql.rows<{ id: string }>`SELECT id FROM users WHERE name = ${name}`;
```

`sql` 태그는 이 시점에 SQL을 실행하지도, `$1` 같은 placeholder를 고르지도 않습니다. 결과는 SQL 조각(segment)의 배열과 값(parameter)의 배열입니다. pg 어댑터가 이 둘을 PostgreSQL 형식으로 바꾸면 다음과 같습니다.

```text
SQL:    SELECT id FROM users WHERE name = $1
values: ["'; DROP TABLE users; --"]
```

공격 문자열은 SQL 텍스트에 들어가지 않고 평범한 값으로 전달됩니다. 이 분리는 내부 불변식으로 고정되어 있습니다.

```text
segments.length === parameters.length + 1
```

SQL 조각은 항상 값보다 하나 많습니다. 값이 없으면 조각 하나, 값이 하나면 조각 둘입니다. 렌더링된 파라미터는 언제나 값이며, 식별자나 중첩 쿼리나 placeholder 문자열이 될 수 없습니다. 이 규칙 덕분에 `$1`, `?`, `:1`, `@p1` 중 무엇을 쓸지는 드라이버 어댑터가 정하고, 같은 쿼리 모델을 PostgreSQL, MySQL, Oracle, SQL Server에 그대로 쓸 수 있습니다.

### 구조는 명시적인 helper로

테이블 이름이나 정렬 컬럼처럼 값이 아닌 SQL 구조가 필요할 때가 있습니다. 이때는 보간 대신 이름이 붙은 helper를 씁니다.

```ts
const sortColumn = "name";
const ids = ["1", "2", "3"];

const query = sql.rows<UserRow>`
  SELECT id, name FROM users
  WHERE id IN (${sql.list(ids)})
  ORDER BY ${sql.ident(sortColumn)}
`;
```

```text
SELECT id, name FROM users
WHERE id IN ($1, $2, $3)
ORDER BY "name"
```

`sql.ident`는 식별자를 dialect 규칙에 맞게 인용하고, `sql.list`는 값 목록을 바인딩 파라미터 여러 개로 펼칩니다. 조각을 조합할 때는 `sql.fragment`와 `sql.join`을 씁니다. 검증된 SQL 텍스트를 그대로 넣는 `sql.raw`도 있지만, 이름 그대로 의도적인 탈출구입니다. 코드 리뷰에서 `sql.raw`만 검색하면 위험 지점이 모두 보이도록 하는 것이 목적입니다.

## 동적 SQL은 SQL 주석으로

MyBatis의 동적 SQL은 XML 태그입니다.

```xml
<select id="findUsers" resultType="User">
  SELECT id, name FROM users
  <where>
    <if test="name != null">AND name = #{name}</if>
    <if test="status != null">AND status = #{status}</if>
  </where>
</select>
```

SQLBraid는 같은 구조를 SQL 블록 주석으로 씁니다.

```ts
function findUsers(name?: string, status?: string) {
  return sql.rows<UserRow>`
    SELECT id, name FROM users
    /*@braid where*/
      /*@braid if ${name != null}*/ AND name = ${name} /*@braid end*/
      /*@braid if ${status != null}*/ AND status = ${status} /*@braid end*/
    /*@braid end*/
  `;
}
```

`findUsers("Ada")`는 다음 SQL이 됩니다.

```text
SELECT id, name FROM users
WHERE name = $1
```

`where`는 MyBatis의 `<where>`처럼 앞에 붙은 `AND`나 `OR`를 정리하고, 남은 조건이 없으면 `WHERE` 자체를 넣지 않습니다. `UPDATE`에서는 `set`이 끝의 쉼표를 정리합니다. 지원하는 지시어는 `if`, `choose`, `when`, `otherwise`, `where`, `set`, `trim`입니다.

주석 형식을 고른 이유는 SQL 도구와의 호환성입니다. 지시어를 지워도 남는 텍스트는 SQL이고, SQL 편집기나 포매터 입장에서 `/*...*/`는 그냥 주석입니다. 템플릿 언어를 새로 배우지 않고 MyBatis의 조건부 SQL 감각을 그대로 가져올 수 있습니다.

### 꺼진 분기의 식도 평가된다

여기에는 JavaScript tagged template의 한계가 하나 있습니다. 태그 함수가 호출되기 전에 모든 `${...}` 식이 먼저 평가됩니다. `if` 조건이 거짓이어도 그 분기 안의 식은 실행됩니다.

```ts
function searchUsers(keyword?: string) {
  return sql.rows<UserRow>`
    SELECT id, name FROM users
    /*@braid where*/
      /*@braid if ${keyword != null}*/
        AND name LIKE ${"%" + keyword + "%"}
      /*@braid end*/
    /*@braid end*/
  `;
}
```

`keyword`가 `undefined`이면 렌더링된 SQL에는 `LIKE` 조건이 없지만, `"%" + keyword + "%"`는 이미 계산되어 `"%undefined%"`가 됩니다. 값은 버려지므로 결과는 맞습니다. 그러나 `${user.name}`처럼 `user`가 없을 때 예외를 던지는 식이라면, 분기가 꺼져 있어도 `TypeError`가 납니다.

이 문제는 라이브러리 런타임만으로는 해결할 수 없습니다. 그래서 선택적 빌드 단계인 `@sqlbraid/compiler`(Vite에서는 `@sqlbraid/vite`)를 따로 두었습니다. 컴파일러는 `@braid` 지시어가 있는 템플릿만 찾아서, 분기 안의 식을 조건이 참일 때만 평가하는 코드로 낮춥니다(lowering). 위 함수를 컴파일한 결과의 핵심 부분은 다음과 같습니다.

```js
if (__sqlbraidAssertCondition(__sqlbraidRead(0, () => keyword != null))) {
    __sqlbraidRead(1, () => "%" + keyword + "%");
}
```

조건식과 분기 안의 값이 각각 thunk로 감싸지고, 조건이 참일 때만 두 번째 식이 평가됩니다. 컴파일러는 이 지시어만 처리합니다. 일반 SQL을 파싱하거나 최적화하는 SQL 컴파일러는 아닙니다.

## 결과 타입과 결과 검증은 다르다

`sql.rows<UserRow>`의 타입 인자는 TypeScript에게 결과 모양을 알려 줄 뿐, 런타임에 행을 검사하지 않습니다. 데이터베이스가 실제로 무엇을 돌려주는지 확인하고 싶다면 [Standard Schema](https://standard-schema.dev/)를 구현한 스키마(Zod, Valibot, ArkType 등)를 넘깁니다.

```ts
import { z } from "zod";

const User = z.object({
  id: z.string(),
  name: z.string(),
});

// 타입만 선언
const rows = await db.all(sql.rows<UserRow>`SELECT id, name FROM users`);

// 런타임 검증과 변환
const user = await db.one(sql.rows(User)`SELECT id, name FROM users WHERE id = ${userId}`);
```

`id`가 `string`인 이유도 여기서 설명할 수 있습니다. SQLBraid는 정수와 decimal을 정확한 문자열로, 부동소수점만 JavaScript `number`로 돌려줍니다. PostgreSQL `bigint` 컬럼에 `9007199254740993`이 있으면 결과는 문자열 `"9007199254740993"`입니다. 이것을 `Number`로 바꾸면 `9007199254740992`가 됩니다. 조용히 틀린 숫자를 돌려주는 대신, 변환 여부를 애플리케이션이 스키마에서 결정하게 했습니다.

## 하지 않기로 한 것

SQL을 그대로 두기로 했기 때문에 일부러 하지 않는 일도 분명합니다.

- 임의의 SQL을 파싱해서 결과 타입을 추론하지 않습니다.
- 커넥션 풀을 구현하지 않습니다. `pg.Pool` 같은 드라이버의 풀을 그대로 받습니다.
- 쿼리를 재시도하거나 다른 연결로 라우팅하지 않습니다.
- 드라이버가 지원하지 않는 기능을 흉내 내지 않습니다. 예를 들어 행 커서 API가 없는 libSQL이나 Cloudflare D1에서 `db.stream()`을 부르면 결과를 전부 버퍼링해서 스트림인 척하지 않고 `BRAID_STREAM_UNSUPPORTED` 오류를 냅니다.

비슷한 위치의 도구와 비교하면 다음과 같습니다. 각 도구의 공식 README를 기준으로 정리했습니다.

| | SQL 작성 방식 | 동적 SQL | 대상 데이터베이스 |
|---|---|---|---|
| ORM | 모델에서 생성 | ORM API | 여러 DB |
| [Kysely](https://github.com/kysely-org/kysely) | TypeScript 쿼리 빌더 | 메서드 체인의 조건 분기 | 여러 DB |
| [Slonik](https://github.com/gajus/slonik) | SQL tagged template | 조각 조합 | PostgreSQL |
| SQLBraid | SQL tagged template | SQL 주석 지시어 | 여러 DB와 드라이버 |

SQLBraid가 지원하는 조합은 PostgreSQL(`pg`), MySQL(`mysql2`), MariaDB, SQLite(`node:sqlite`, `better-sqlite3`, `@libsql/client`, SQLite WASM, Cloudflare D1), Oracle(`oracledb`), SQL Server(`tedious`), Bun.SQL입니다. 지원 여부는 "PostgreSQL 지원"처럼 뭉뚱그리지 않고 데이터베이스, 드라이버, 런타임, 기능의 조합 단위로 [지원 표](https://clickin.github.io/SQLBraid/latest/reference/support/)에 기록합니다.

## 시작하기

```sh
npm install sqlbraid pg
```

드라이버마다 `sqlbraid/pg`, `sqlbraid/mysql2`, `sqlbraid/node-sqlite` 같은 하위 경로를 import합니다. 설치 없이 바로 돌려 보려면 Node.js 22.18 이상에서 `node:sqlite`를 쓰는 [빠른 시작](https://clickin.github.io/SQLBraid/latest/getting-started/sqlite/)이 가장 간단합니다. 이 밖에 CLI, 데이터베이스 메타데이터에서 TypeScript 모델을 생성하는 codegen, VS Code 확장, OpenTelemetry 연동이 있습니다.

정리하면 SQLBraid는 SQL을 대신 써 주는 도구가 아닙니다. 사용자가 쓴 SQL에서 값과 구조의 경계를 지키고, 조건부 SQL을 SQL답게 표현하게 해 주는 도구입니다. 그러면 라이브러리에 남는 어려운 일은 무엇일까요? 답은 SQL 바깥, 연결과 트랜잭션의 수명에 있습니다. [다음 글](/blog/2026-10-06-sqlbraid-2-execution-path/)에서 그 이야기를 합니다.
