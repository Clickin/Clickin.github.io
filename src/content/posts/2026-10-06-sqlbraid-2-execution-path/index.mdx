> English version: [SQLBraid Dev Notes 2: One Query's Path, from Value Binding to Connection Release](/blog/2026-10-06-sqlbraid-2-execution-path-en/)

[첫 번째 글](/blog/2026-10-06-sqlbraid-1-why-sql-first/)에서는 SQLBraid가 SQL을 그대로 두고 값과 구조의 경계만 지킨다고 설명했습니다. 그러면 라이브러리 코드의 대부분은 어디에 쓰일까요? SQLBraid 런타임 코드의 대부분은 SQL 처리가 아니라 연결, 트랜잭션, 스트림 같은 물리적 자원을 누가 언제까지 소유하는지를 다룹니다.

이 글은 `db.all()` 한 번이 거치는 경로를 따라가면서, 각 단계에서 SQLBraid가 지키는 규칙을 설명합니다. 예제는 SQLBraid v1.0.2, PostgreSQL 16, `pg` 8.23.0으로 실행했고, 출력은 실제 실행 결과입니다.

## 전체 경로

풀에서 동작하는 `db.all(query)`는 다음 순서로 실행됩니다. 핵심은 연결을 쥐고 있는 구간이 드라이버 I/O 앞뒤로 최대한 짧다는 점입니다.

| 단계 | 하는 일 | 연결 |
|---|---|---|
| `render()` | SQL 조각과 값 목록 생성 | 없음 |
| `binding.describe()` | `$1` placeholder SQL 생성 | 없음 |
| 대여 | pool에서 lease 획득 | 대여 중 |
| 드라이버 I/O | 쿼리 실행, 결과 수신 | 대여 중 |
| 반납 | lease를 pool에 반납 | 반납함 |
| 결과 종류 확인 | rows/command 등 기대한 결과인지 확인 | 없음 |
| 결과 검증 | Standard Schema 검증과 변환 | 없음 |

## 연결을 빌리기 전: 렌더링과 바인딩 설명

`sql` 태그가 만든 `Query`는 아직 물리적인 SQL이 아닙니다. `render()`는 SQL 조각과 값 목록을 만들고, 드라이버 어댑터의 `StatementBindingAdapter`가 이것을 드라이버 형식으로 바꿉니다. pg 어댑터의 결과는 다음과 같습니다.

```ts
const query = sql.rows<UserRow>`SELECT id, name FROM users WHERE id = ${1} AND name = ${"Ada"}`;
```

```text
parameterizedSql: SELECT id, name FROM users WHERE id = $1 AND name = $2
transport:        text-positional
reuse:            { requested: "auto", effective: "simple", owner: "driver" }
```

MySQL 어댑터라면 같은 쿼리가 `?`로, Oracle은 `:1`로, SQL Server는 `@p1`로 바뀝니다. 쿼리 모델은 그대로이고 placeholder 문법만 어댑터가 책임집니다.

이 단계는 순수 함수이고 연결을 빌리기 전에 실행됩니다. 지원하지 않는 바인딩 힌트나 잘못된 파라미터는 여기서 실패합니다. 실패할 쿼리 때문에 풀의 연결을 붙잡는 일이 없습니다.

### prepare는 서버 캐시를 약속하지 않는다

`db.prepare()`도 이 단계에서 동작합니다. 이름 때문에 서버 쪽 prepared statement를 떠올리기 쉽지만, SQLBraid의 prepare가 약속하는 것은 논리적인 쿼리 모양(shape)이 고정된다는 것입니다. 첫 실행이 결과 종류, SQL 조각, 파라미터 순서를 확정하고, 이후에는 값만 바뀔 수 있습니다.

```ts
const byName = db.prepare("users-by-name", (name: string | null) => sql.rows<{ id: string }>`
  SELECT id FROM users
  /*@braid where*/
    /*@braid if ${name != null}*/ AND name = ${name} /*@braid end*/
  /*@braid end*/
`);

await byName.all("Ada");     // [{ id: "1" }], 모양이 고정됨
await byName.all(null);      // BRAID_PREPARED_SHAPE
```

두 번째 호출은 동적 분기 때문에 `WHERE` 절이 사라져 SQL 구조가 달라집니다. SQLBraid는 드라이버 I/O 전에 `BRAID_PREPARED_SHAPE`로 거부합니다. 실제로 서버에서 statement를 재사용하는지는 어댑터가 따로 보고합니다. 앞의 출력에서 pg 어댑터가 `effective: "simple"`로 보고한 것이 그 예입니다. 지원하지 않는 재사용을 지원하는 것처럼 표시하지 않습니다.

## 결과 검증 전에 연결을 돌려준다

드라이버 I/O가 끝나고 결과 행이 메모리에 올라오면, SQLBraid는 Standard Schema 검증을 실행하기 전에 연결을 풀에 돌려줍니다. 비동기 스키마 안에서 풀 상태를 출력해 보면 확인할 수 있습니다.

```ts
const pool = new pg.Pool({ max: 4 /* ... */ });
const db = createPgPoolDatabase(pool);

const User = z
  .object({ id: z.string(), name: z.string() })
  .transform(async (row) => {
    console.log(`total=${pool.totalCount} idle=${pool.idleCount}`);
    return row;
  });

await db.all(sql.rows(User)`SELECT id, name FROM users`);
```

```text
total=1 idle=1
```

연결 하나가 만들어졌고, 스키마가 실행되는 시점에는 이미 유휴 상태입니다. 검증이나 변환이 느려도, 예를 들어 행마다 외부 값을 조회하는 변환이 있어도 데이터베이스 연결을 붙잡지 않습니다. 풀의 연결 수는 한정되어 있으므로 애플리케이션 코드가 연결을 점유하는 시간을 줄이는 것이 목적입니다.

## 스트림은 연결을 계속 쥔다

스트림은 반대로 동작합니다. `db.stream()`은 결과를 전부 받은 뒤 나눠 주는 `all()`이 아니라, 드라이버의 커서(pg에서는 `pg-cursor`)를 실제로 엽니다. 커서가 살아 있는 동안 연결도 필요합니다.

```ts
for await (const row of db.stream(sql.rows<{ g: string }>`
  SELECT g::text AS g FROM generate_series(1, 1000) g
`)) {
  console.log(`total=${pool.totalCount} idle=${pool.idleCount}`, row);
  break;
}
console.log(`total=${pool.totalCount} idle=${pool.idleCount}`);
```

```text
total=1 idle=0 { g: '1' }
total=1 idle=1
```

반복 중에는 연결이 대여 상태이고, `break`로 빠져나오면 커서를 정리한 다음 연결이 풀로 돌아갑니다. 예외, 취소, 스키마 검증 실패도 같은 정리 경로를 탑니다. 드라이버 커서 정리가 먼저, 연결 반납이 나중입니다.

앞의 글에서 말했듯이 행 커서 API가 없는 드라이버는 `db.stream()`을 `BRAID_STREAM_UNSUPPORTED`로 거부합니다. 전부 버퍼링한 결과를 스트림처럼 보이게 하면 이 글에서 설명한 메모리와 연결 보장이 모두 거짓이 되기 때문입니다.

## session과 tx는 연결 하나를 고정한다

풀에 동시에 보낸 루트 쿼리는 서로 다른 연결에서 실행될 수 있습니다. `pg_backend_pid()`로 확인해 보면 다음과 같습니다.

```ts
const pid = () => sql.rows<{ pid: string }>`SELECT pg_backend_pid()::text AS pid, pg_sleep(0.2)::text AS s`;

await Promise.all([db.one(pid()), db.one(pid())]);
// pid: 1304, 1305

await db.session((s) => Promise.all([s.one(pid()), s.one(pid())]));
// pid: 1305, 1305
```

`db.session()`은 트랜잭션 없이 연결 하나를 콜백 동안 고정합니다. 임시 테이블이나 세션 변수처럼 연결에 붙은 상태를 써야 할 때 사용합니다. `db.tx()`는 연결 하나를 고정하고 그 위에서 트랜잭션을 시작합니다. 안쪽에서 다시 `tx.tx()`를 부르면 새 트랜잭션이 아니라 같은 연결 위의 savepoint가 됩니다.

```text
db.tx(outer)       BEGIN
  outer.tx(inner)  SAVEPOINT
                   RELEASE SAVEPOINT  (콜백 실패 시 ROLLBACK TO SAVEPOINT 후 RELEASE)
                   COMMIT
```

격리 수준 같은 트랜잭션 옵션은 바깥 트랜잭션에만 줄 수 있습니다. 안쪽 `tx(options, callback)`은 거부합니다. 이미 시작된 트랜잭션의 격리 수준을 바꾸는 척하는 의미를 만들지 않기 위해서입니다.

## 핸들이 범위를 벗어나면 거부한다

트랜잭션이 연결 하나에 고정된다는 약속은, 콜백 안에서 다른 핸들로 쿼리를 보내면 쉽게 깨집니다. 트랜잭션 안에서 실수로 바깥 `db`를 쓰면 그 쿼리는 다른 연결에서, 트랜잭션 밖에서 실행됩니다. SQLBraid는 이런 경우를 다른 연결로 보내지 않고 오류로 막습니다.

```ts
await db.tx(async (tx) => {
  await db.all(sql.rows`SELECT 1`);     // BRAID_TX_SCOPE: 루트 핸들 사용
});

let leaked: Database | undefined;
await db.tx(async (tx) => { leaked = tx; });
await leaked!.all(sql.rows`SELECT 1`);  // BRAID_TX_CLOSED: 끝난 트랜잭션 핸들

await db.tx(async (tx) => {
  await tx.tx(async (inner) => {
    await tx.all(sql.rows`SELECT 1`);   // BRAID_TX_SCOPE: savepoint 안에서 부모 핸들 사용
  });
});

await db.session(async (s) => {
  for await (const row of s.stream(sql.rows`SELECT g FROM generate_series(1, 10) g`)) {
    await s.all(sql.rows`SELECT 1`);    // BRAID_STREAM_SCOPE: 같은 연결의 스트림이 열려 있음
  }
});
```

마지막 경우는 드라이버마다 동작이 다릅니다. 같은 연결에서 커서가 열려 있는 동안 다른 쿼리를 보내면, 어떤 드라이버는 큐에 넣고 어떤 드라이버는 실패하고 어떤 드라이버는 정의되지 않은 상태가 됩니다. SQLBraid는 드라이버의 정의되지 않은 동작에 기대지 않고 먼저 거부합니다.

## COMMIT이 COMMIT으로 끝나지 않을 때

PostgreSQL에서는 트랜잭션 안의 문장 하나가 실패하면 트랜잭션 전체가 중단(aborted) 상태가 됩니다. 이 상태에서 `COMMIT`을 보내면 오류가 아니라 롤백이 일어납니다. 직접 `pg`로 확인하면 다음과 같습니다.

```ts
const client = await pool.connect();
await client.query("BEGIN");
try { await client.query("SELECT 1/0"); } catch {}
const result = await client.query("COMMIT");
console.log(result.command);
```

```text
ROLLBACK
```

`COMMIT` 호출은 성공적으로 끝났고 예외도 없습니다. 결과 객체의 `command`를 확인하지 않으면 커밋되었다고 믿게 됩니다. 애플리케이션 코드에서 이 상황은 생각보다 쉽게 만들어집니다. 트랜잭션 콜백 안에서 오류를 잡아 삼키면 됩니다.

```ts
await db.tx(async (tx) => {
  await tx.execute(sql.command`INSERT INTO ledger VALUES (1)`);
  try {
    await tx.all(sql.rows`SELECT 1/0`);
  } catch {
    // 오류를 기록만 하고 계속 진행
  }
});
```

```text
BRAID_TX_NOT_COMMITTED: PostgreSQL COMMIT completed with ROLLBACK, not COMMIT.
```

SQLBraid의 pg 어댑터는 `COMMIT`의 결과가 `COMMIT`이 아니면 `BRAID_TX_NOT_COMMITTED`로 실패합니다. 위 예제 실행 후 `ledger` 테이블의 행 수는 0이었습니다. `db.tx()`가 정상 완료되었다면 데이터가 저장되었다는 뜻이어야 하므로, 그렇지 않은 경우를 성공으로 돌려주지 않습니다. Bun.SQL의 PostgreSQL 어댑터도 같은 검사를 합니다.

## 불확실한 연결은 버린다

트랜잭션 제어, 스트림 정리, 취소 중 하나가 실패하면 연결이 어떤 상태인지 확신할 수 없게 됩니다. 롤백이 실제로 실행되었는지, 커서가 닫혔는지 모르는 연결을 풀에 돌려주면 다음 사용자가 그 상태를 물려받습니다.

SQLBraid는 이런 연결을 오염(poisoned) 상태로 표시합니다. 풀에서 빌린 연결이면 반납하지 않고 폐기(discard)하고, 직접 넘겨받은 단일 연결이면 이후 모든 작업을 거부합니다. 정리 과정에서 실패가 여러 번 나도 처음 발생한 오류를 감추지 않고, 정리 실패는 모아서 함께 보고합니다. 연결을 낙관적으로 재사용하는 것보다 정확성이 우선입니다.

## 테스트로 지키는 규칙

이 글에서 설명한 동작은 모두 저장소의 아키텍처 문서([mental model](https://github.com/Clickin/SQLBraid/blob/v1.0.2/docs/mental-model.md))에 불변식으로 적혀 있습니다. 요약하면 다음과 같습니다.

- 일반 보간은 언제나 값 바인딩이다.
- 바인딩 설명은 순수하며 연결 대여 전에 실행된다.
- 풀에서 실행한 결과는 애플리케이션 매핑 전에 연결을 반납한다.
- 스트림은 드라이버 정리가 끝날 때까지 연결을 쥔다.
- session은 트랜잭션 없이 연결을 고정하고, 중첩 트랜잭션은 같은 연결의 savepoint다.
- 루트나 부모 핸들로의 범위 이탈은 다른 연결로 보내지 않고 거부한다.
- 불확실한 연결은 오염 처리하거나 폐기한다.
- 지원하지 않는 기능은 흉내 내지 않고 명시적으로 실패한다.

저장소에는 이 규칙들을 검사하는 계약 테스트와, 드라이버별로 실제 데이터베이스에 붙여 실행하는 테스트가 있습니다. 지원 표의 항목은 이 테스트 결과를 근거로 기록합니다.

## 마치며

SQLBraid의 SQL 쪽 표면은 작습니다. 태그 하나, helper 몇 개, 주석 지시어 몇 개가 전부입니다. 대신 런타임은 "연결을 언제 빌리고 언제 돌려주는가", "이 핸들이 아직 유효한가", "커밋이 정말 커밋되었는가"에 대부분의 코드를 씁니다. SQL을 직접 쓰는 도구라면 SQL 생성보다 이 부분을 맡는 것이 라이브러리의 몫이라고 생각했습니다.

현재 버전은 1.0.2이고, SQL 파일 기반 마이그레이션 도구(`@sqlbraid/migrate`)를 준비하고 있습니다. 사용해 보시고 문제나 의견이 있으면 [GitHub 저장소](https://github.com/Clickin/SQLBraid)에 이슈로 남겨 주세요.
