> English version: [SQLBraid Dev Notes 2: One Query's Path, from Value Binding to Connection Release](/blog/2026-10-06-sqlbraid-2-execution-path-en/)

[지난 글](/blog/2026-10-06-sqlbraid-1-why-sql-first/)에서는 SQLBraid가 SQL 의미 분석을 내려놓고, 대신 값 바인딩·결과 선언·연결과 트랜잭션 수명을 맡기로 한 과정을 정리했습니다. 이번 글은 그 책임을 코드에서 어떻게 지키는지 봅니다.

질문은 이것입니다. **같은 쿼리를 여러 driver에서 실행해도 값·결과·물리 자원의 규칙을 어떻게 유지하는가?** 패키지 순서로 설명하지 않고, 지난 글의 검색 쿼리 하나를 pool에서 실행하는 정상 경로를 끝까지 따라간 다음, 같은 쿼리를 트랜잭션과 스트림으로 바꿔 무엇이 달라지는지 보겠습니다.

```ts
function searchProducts(filter: { keyword?: string; maxPrice?: number }) {
  return sql.rows<ProductRow>`
    SELECT id, name, price
    FROM products
    /*@braid where*/
      /*@braid if ${filter.keyword != null}*/
        AND name ILIKE ${"%" + filter.keyword + "%"}
      /*@braid end*/
      /*@braid if ${filter.maxPrice != null}*/
        AND price <= ${filter.maxPrice}
      /*@braid end*/
    /*@braid end*/
    ORDER BY id
  `;
}

const rows = await db.all(searchProducts({ keyword: "lamp" }));
```

글의 출력 예시는 SQLBraid 1.0.2 기준 저장소 빌드와 로컬 PostgreSQL 16 컨테이너, `pg` 8.23.0에서 직접 실행해 확인한 값입니다. 코드 링크는 [`v1.0.2` 태그](https://github.com/Clickin/SQLBraid/tree/v1.0.2)를 가리킵니다.

## tagged template는 실행 요청이 되기 전에 무엇이 되는가

`searchProducts()`가 돌려주는 것은 SQL 문자열이 아니라 `Query` 객체입니다. `Query`는 template의 구조(IR), tag 호출 시점에 평가된 값 목록, 그리고 `rows`/`command`/`call` 같은 결과 종류를 들고 있습니다. 아직 placeholder도 없고 driver도 모릅니다.

`query.render()`를 호출하면 directive가 풀리고 `RenderedStatement`가 나옵니다. `{ keyword: "lamp" }`로 만든 쿼리를 보면 둘의 차이가 드러납니다. 이하 출력은 읽기 쉽게 들여쓰기 공백만 줄였습니다.

```text
query.values          [true, "%lamp%", false, null]

rendered.segments     ["\n SELECT id, name, price\n FROM products\n WHERE name ILIKE ",
                       "\n ORDER BY id\n "]
rendered.parameters   ["%lamp%"]
```

`query.values`에는 조건식 결과(`true`, `false`)와 비활성 분기의 값(`null`)까지 네 개가 들어 있습니다. 렌더링은 그중 활성 분기의 값만 parameter로 고르고, `where`가 맨 앞 `AND`를 지우고 `WHERE`를 붙인 SQL 조각을 segment로 남깁니다.

`RenderedStatement`가 항상 지키는 규칙은 하나입니다.

```text
segments.length === parameters.length + 1
```

SQL 구조는 전부 segment에 있고, parameter는 전부 값입니다. 위 예에서는 segment 2개, parameter 1개입니다. 조건을 모두 끄면 segment 1개, parameter 0개가 됩니다. parameter가 식별자나 SQL 조각으로 해석되는 경로는 없습니다. `${"x' OR '1'='1"}`을 넣어도 parameter 배열에 그 문자열이 그대로 하나 들어갈 뿐입니다.

구조를 바꾸려면 helper가 segment 쪽에 글자를 넣어야 합니다.

```ts
sql.rows`SELECT id FROM products ORDER BY ${sql.ident("price")} DESC LIMIT ${10}`;
```

```text
segments    ['SELECT id FROM products ORDER BY "price" DESC LIMIT ', ""]
parameters  [10]
```

`sql.ident`는 dialect 규칙으로 식별자를 quote해서 segment에 넣고, `10`은 parameter로 남습니다. `sql.raw(text)`도 segment에 글자를 넣지만 quote 없이 그대로 넣습니다. 이 경계를 넘는 유일한 helper이므로 외부 입력을 넣으면 안 됩니다.

### 비활성 분기는 왜 별도 변환이 필요한가

`query.values`에서 눈여겨볼 점이 있습니다. `maxPrice`의 값은 `null`로 들어 있고, `keyword`가 없을 때는 `"%undefined%"`가 들어갑니다. JavaScript는 tag 함수를 호출하기 전에 모든 `${...}`를 평가하기 때문입니다. directive는 주석이라서 JavaScript 평가 순서에 영향을 주지 못합니다.

값이 버려지기만 하면 괜찮지만, 평가 자체가 실패할 수 있습니다.

```ts
const user: { name: string } | null = null;
sql.rows`SELECT id FROM users
  /*@braid where*/
    /*@braid if ${user != null}*/ AND name = ${user.name} /*@braid end*/
  /*@braid end*/`;
// TypeError: Cannot read properties of null (reading 'name')
```

TypeScript도 이 코드를 거부합니다. `if` directive는 주석이라 control-flow narrowing이 일어나지 않고, `user.name`에 TS18047(`'user' is possibly 'null'`)이 보고됩니다.

`@sqlbraid/compiler`는 directive가 있는 template만 찾아 다른 호출로 바꿉니다. 실제 변환 결과에서 핵심만 줄이면 이렇습니다.

```ts
__sqlbraidCapture(sql.rows<ProductRow>, strings, (__sqlbraidValues) => {
  const __sqlbraidRead = (index, thunk) => {
    if (!__sqlbraidEvaluated.has(index)) {
      __sqlbraidValues[index] = thunk();
      __sqlbraidEvaluated.add(index);
    }
    return __sqlbraidValues[index];
  };
  if (__sqlbraidAssertCondition(__sqlbraidRead(0, () => filter.keyword != null))) {
    __sqlbraidRead(1, () => "%" + filter.keyword + "%");
  }
}, templateIr);
```

각 interpolation이 thunk로 감싸지고, 원래 directive 구조가 실제 `if` 문이 됩니다. 그래서 세 가지가 함께 보장됩니다. 비활성 분기의 식은 평가되지 않고, 각 식은 `Set`으로 한 번만 평가되며, 진짜 `if` 안에 있으니 TypeScript narrowing이 적용됩니다. 저장소의 테스트는 lowering된 가상 소스로 type check했을 때 `user != null` 분기 안의 `user.name`에서 TS18047이 사라지고, 조건이 무관한 `enabled`일 때는 원래 소스 위치에 TS18047이 남는 것을 확인합니다.

이 보장은 tag만으로는 생기지 않습니다. 빌드 단계에서 compiler(Vite 통합 등)를 거친 소스에만 해당합니다. compiler는 directive lowering만 하고 SQL을 파싱하지 않습니다.

## logical statement를 native driver 요청으로 바꾸는 경계

`RenderedStatement`에는 `$1`이 없습니다. placeholder 문법은 dialect가 아니라 driver adapter의 `StatementBindingAdapter`가 정합니다. PostgreSQL `pg` adapter의 `describe()` 결과는 이렇습니다.

```text
transport          text-positional
parameterizedSql   SELECT id, name, price FROM products WHERE name ILIKE $1 ORDER BY id
reuse              { requested: "auto", effective: "simple", owner: "driver" }
```

같은 segment/parameter 배열을 MySQL adapter는 `?`로, Oracle adapter는 `:1`로, SQL Server adapter는 `@p1`과 typed request로 바꿉니다. driver가 tagged template을 직접 받는 경우를 위한 `native-value-template` transport도 있습니다. logical statement 모양은 transport와 상관없이 같습니다.

순서도 정해져 있습니다. `describe()`는 순수 함수이고 **연결을 얻기 전에** 실행됩니다. parameter hint가 잘못됐거나 adapter가 지원하지 않는 바인딩이면 pool lease를 하나도 쓰지 않고 실패합니다. 연결을 얻은 뒤에는 lease의 `statementBinding`이 미리 description을 만든 adapter와 같은 객체인지 확인합니다. 다르면 그 lease를 discard하고 거부합니다. 다른 규칙으로 만든 placeholder SQL이 엉뚱한 driver로 가는 것을 막기 위해서입니다.

### `db.prepare()`는 무엇을 고정하는가

`reuse` 필드는 prepared statement와 관련이 있습니다. README의 `db.prepare()` 예제를 다시 보다가 이 API가 정말 필요한지 의문이 들었습니다. 일반 함수로 만들어도 bind variable은 어차피 lexical scope에서 캡처되기 때문입니다.

따져 보니 실제로 일반 함수도 같은 바인딩을 만들었습니다. `searchProducts()` 자체가 그 예입니다. 그래서 `prepare`의 역할을 다시 정의했습니다. `db.prepare()`가 따로 하는 일은 **logical shape lock**입니다. 첫 실행의 result kind, dialect, segment, parameter metadata를 기억하고, 다음 실행에서 구조가 바뀌면 driver I/O 전에 거부합니다.

```ts
const prepared = db.prepare("search", (f: ProductFilter) => searchProducts(f));
await prepared.all({ keyword: "lamp" });
await prepared.all({ keyword: "lamp", maxPrice: 1 });
// BRAID_PREPARED_SHAPE: Prepared query search changed its rendered structure.
```

directive로 분기가 바뀌면 segment가 달라지므로, 동적 검색 쿼리는 `prepare` 대상이 아닙니다. 그리고 shape lock은 서버 쪽 prepared statement 재사용과 별개입니다. `pg` adapter는 `requested: "reuse"`를 받아도 `effective: "simple"`로 보고하고, 매번 `client.query({ text, values })`로 실행합니다. 그래서 README에서 `prepare`가 성능을 높인다는 문구를 지우고, 실제 재사용 여부는 adapter가 정한다고 고쳤습니다.

## 실행과 결과 mapping 사이에서 connection을 언제 반환하나

`db`가 무엇을 감싸고 있는지에 따라 이후 경로가 달라집니다.

- `createPgDatabase(client)`는 이미 연결된 물리 client 하나를 감싸는 **direct executor**입니다. SQLBraid는 그 client의 사용을 직렬화하지만 종료는 책임지지 않습니다.
- `createPgPoolDatabase(pool)`은 `ConnectionProvider`를 감쌉니다. provider는 물리 연결을 빌려주는 곳이고, 빌린 연결 하나가 `ConnectionLease`입니다.

같은 pool 객체에 쿼리를 보낸다고 같은 연결을 쓰는 것은 아닙니다. 같은 `db`로 세 쿼리를 동시에 보내면 PostgreSQL backend pid가 셋 다 다르게 나옵니다.

```text
db.one(pid) × 3 (동시)        → ["85", "84", "86"]
db.session(s => s.one(pid) × 3) → ["86", "86", "86"]
```

pool에서 `db.all()`을 한 번 호출하면 런타임은 이 순서로 움직입니다.

```text
render + binding.describe   연결 없이 수행
provider.acquire()          lease 획득
executor.query()            driver I/O, TypePolicy로 값 정규화, 행 materialize
lease.release()             연결 반환
result-kind 검사            rows 선언에 command 결과가 오면 실패
Standard Schema mapping     애플리케이션 검증·변환
```

`runPrepared()`의 주석이 이 순서의 이유를 적고 있습니다.[^materialized]

```ts
// Materialize and release before Standard Schema mapping so pooled connections are not held during application code.
const raw = await physical(operation, use!, executionOptions);
...
await use!.release(isPoisoned(use!.physicalState));
```

`db.all()`의 결과는 이미 메모리에 다 올라온 배열입니다. 그 뒤의 schema 검증은 비동기일 수 있고 애플리케이션 코드가 얼마나 오래 걸릴지 알 수 없습니다. 그 시간 동안 개수가 정해진 pool 연결을 붙잡을 이유가 없습니다. schema의 `validate` 안에서 pool 상태를 찍어 보면, mapping 중에 연결이 이미 idle로 돌아가 있습니다.

```text
query:ready → query:result → map(total=1, idle=1) ×3 → query:mapped
```

이 순서는 pool root 작업에 해당합니다. 트랜잭션이나 session 안에서는 `release()`가 lease를 돌려주지 않고 그 연결에 대한 실행 순번만 풉니다. 연결은 scope가 끝날 때 한 번 반환됩니다.

result-kind 검사가 I/O 뒤에 온다는 점도 기억해야 합니다. `sql.rows`로 선언한 쿼리에 DML이 들어 있으면 실행 후에야 불일치가 발견됩니다. 이 검사는 부작용을 막지 못합니다.

### 값 정규화와 application mapping은 다른 층이다

위 표에서 값 정규화는 driver I/O 단계에, schema mapping은 반환 이후에 있습니다. 둘은 목적이 다릅니다.

- **TypePolicy**는 driver가 준 값을 SQLBraid의 기본 JavaScript 표현으로 바꿉니다. exact integer·decimal은 문자열, IEEE 근삿값은 number입니다.
- **Standard Schema**는 그 기본 표현을 애플리케이션 타입으로 바꿉니다. decimal 문자열을 `Decimal`이나 `Money` 객체로 바꾸는 것은 여기서 합니다.

TypePolicy가 driver 단계에 있어야 하는 이유는 정밀도 사례가 보여 줍니다. id가 `9007199254740993`, price가 `numeric(20,2)`의 `12345678901234567.89`인 행을 읽으면 이렇게 나옵니다.

```text
{ id: "9007199254740993", name: "big id lamp", price: "12345678901234567.89" }
Number("9007199254740993") → 9007199254740992
```

`pg` adapter는 exact numeric OID에 대해 driver의 type parser를 문자열 parser로 덮어써서, 값이 처음부터 number로 바뀌지 않게 합니다. 이미 number로 반올림된 값을 나중에 문자열로 바꿔도 잃은 자릿수는 돌아오지 않습니다. 그래서 이 변환은 mapping 층에서 할 수 없습니다.

이 정책은 driver와 profile마다 근거가 따로 필요합니다. 예를 들어 Bun.SQL의 MySQL/MariaDB DECIMAL은 SQL에서 text로 바꾸지 않으면 거부되고, SQLite의 native decimal은 지원하지 않습니다. JSON 안의 숫자나 native `Date`의 정밀도는 별도 profile 문제입니다. 조합별 범위는 [data representation 문서](https://clickin.github.io/SQLBraid/latest/concepts/data-representation/)와 [limitations](https://clickin.github.io/SQLBraid/latest/release/limitations/)에 있습니다.

## session과 transaction은 물리 자원의 소유권을 바꾼다

pool root 작업은 쿼리마다 lease를 빌리고 바로 돌려줍니다. `session`과 `tx`는 이 소유권을 callback 범위로 늘립니다.

```d2
direction: down

pool: "Pool (ConnectionProvider)"

root: "root 작업" {
  op: "쿼리마다 lease 획득"
  rel: "materialize 후 반환\nmapping 전"
  op -> rel
}

tx: "db.tx() 범위" {
  lease: "lease 1개 고정"
  sp: "nested tx.tx()\n= SAVEPOINT"
  lease -> sp: "같은 연결"
}

stream: "db.stream()" {
  cur: "cursor 열림"
  close: "iterator 종료 후 반환"
  cur -> close
}

pool -> root.op: "acquire"
pool -> tx.lease: "acquire"
pool -> stream.cur: "acquire"
tx.lease -> stream.cur: "tx 안 stream은\n같은 연결 사용" {
  style.stroke-dash: 3
}
```

`db.session(callback)`은 lease 하나를 callback 동안 고정하지만 트랜잭션을 시작하지 않습니다. 위 pid 결과에서 session 안의 쿼리가 모두 같은 연결을 쓴 것이 이것입니다. 연결 단위 설정이나 임시 테이블처럼 같은 연결이 필요하지만 트랜잭션은 필요 없을 때 씁니다.

`db.tx(callback)`은 연결 하나에서 `BEGIN`, callback, `COMMIT` 또는 `ROLLBACK`을 실행합니다. 안에서 다시 `tx.tx()`를 부르면 독립 트랜잭션이 아니라 같은 연결의 savepoint입니다. 그래서 nested 호출에는 isolation 같은 옵션을 줄 수 없습니다(`BRAID_TX_OPTIONS_NESTED`).

savepoint와 callback 범위를 지키려면 handle을 엇갈려 쓰는 것을 막아야 합니다.

```ts
await db.tx(async (tx) => {
  await tx.tx(async (inner) => {
    await tx.all(searchProducts({}));
    // BRAID_TX_SCOPE: Use the innermost transaction database while its savepoint is active.
  });
});

let escaped;
await db.tx(async (tx) => { escaped = tx; });
await escaped.all(searchProducts({}));
// BRAID_TX_CLOSED: Transaction database is no longer usable.
```

savepoint가 열려 있는 동안 바깥 `tx`로 쿼리를 보내면, 그 쿼리가 savepoint 안에 속하는지 밖에 속하는지 애매해집니다. 끝난 트랜잭션의 handle을 다른 연결로 조용히 돌리면 원자성을 기대한 코드가 트랜잭션 밖에서 실행됩니다. SQLBraid는 두 경우 모두 다른 연결로 보내지 않고 거부합니다.

### COMMIT 응답이 ROLLBACK일 때

지난 글의 사례를 실행 경로로 다시 보겠습니다.

```ts
await db.tx(async (tx) => {
  await tx.execute(sql.command`INSERT INTO audit (note) VALUES (${"first"})`);
  try {
    await tx.execute(sql.command`INSERT INTO missing_table VALUES (1)`);
  } catch {
    // relation "missing_table" does not exist
  }
  return "ok";
});
```

`missing_table` 오류로 PostgreSQL 트랜잭션은 aborted 상태가 됩니다. callback은 정상 반환합니다. 런타임은 열린 stream이 없는지 확인한 뒤 adapter의 `commit()`을 호출합니다. `pg`에서 이 `COMMIT`은 예외 없이 끝나고 결과의 `command`가 `"ROLLBACK"`입니다. 그래서 adapter의 transaction control 함수가 응답을 직접 검사합니다.[^pg-commit]

```ts
const runControl = async (text: string): Promise<void> => {
  const result = await client.query({ text, values: [] });
  if (text === "COMMIT" && result.command !== undefined && result.command !== "COMMIT") {
    throw new AdapterError(
      "BRAID_TX_NOT_COMMITTED",
      `PostgreSQL COMMIT completed with ${result.command}, not COMMIT.`,
    );
  }
};
```

그 다음 순서는 런타임의 `tx()`가 정합니다.

```text
callback 정상 반환
  → scope의 열린 stream 정리 확인
  → commit control 실행 → BRAID_TX_NOT_COMMITTED
  → control 실패: 물리 상태를 poisoned로 표시
  → catch: poisoned이므로 ROLLBACK을 다시 보내지 않음
  → finally: pooled lease는 discard로 반환
  → db.tx()는 BRAID_TX_NOT_COMMITTED로 reject
```

COMMIT 결과가 기대와 다르면 그 연결이 지금 어떤 트랜잭션 상태인지 SQLBraid가 확신할 수 없습니다. 이런 연결은 poisoned로 표시합니다. pooled lease라면 `release({ discard: true })`로 pool에 돌려주지 않고 버리게 하고, direct executor라면 이후 모든 작업을 `BRAID_CONNECTION_POISONED`로 거부합니다. 불확실한 연결에 ROLLBACK을 한 번 더 보내 정상으로 되돌리려 하지 않습니다.

실제 PostgreSQL에서 실행하면 `db.tx()`는 `BRAID_TX_NOT_COMMITTED`로 실패하고, `audit` 테이블의 행 수는 0입니다. 저장소의 contract test는 `pg` direct, `pg` pool, Bun.SQL PostgreSQL 세 경로에서 같은 상황을 fixture로 재현합니다. COMMIT이 정확히 한 번 호출됐는지, 그 뒤 pooled lease가 discard로 한 번 반환됐는지, direct 연결이 이후 control I/O에 도달하지 않는지를 확인합니다.[^contract-test]

### 대조 사례: Oracle autoCommit

Oracle에서는 같은 질문, 즉 "누가 commit을 소유하는가"가 다른 모습으로 나왔습니다. `node-oracledb`에는 전역 또는 호출별 `autoCommit` 옵션이 있습니다. 사용자가 `autoCommit: true`를 설정해 둔 상태에서 SQLBraid 관리 트랜잭션 안의 문장도 그 설정을 따르면, 문장마다 먼저 커밋돼서 `db.tx()`의 rollback이 의미를 잃습니다.

Oracle adapter는 트랜잭션이 활성인 동안에만 실행 옵션에 `autoCommit: false`를 덮어씁니다.[^oracle]

```ts
return {
  ...customOptions,
  ...(transactionActive ? { autoCommit: false } : {}),
  ...
};
```

트랜잭션 밖에서는 사용자가 준 옵션을 그대로 둡니다. 관리 트랜잭션 안에서는 commit과 rollback을 SQLBraid가 소유하고, 밖에서는 driver 설정이 소유하는 식으로 경계를 나눴습니다.

## stream은 iteration이 끝날 때까지 연결을 소유한다

`db.all()`과 달리 `db.stream()`은 결과를 다 읽기 전에 행을 넘겨줍니다. PostgreSQL에서는 `pg-cursor`의 cursor가 연결 위에 열려 있어야 다음 행을 읽을 수 있습니다. 따라서 stream은 iteration이 끝날 때까지 lease를 돌려줄 수 없고, schema mapping도 행마다 연결을 쥔 채 수행합니다.

소비자가 중간에 멈추는 경우를 보겠습니다.

```ts
for await (const row of db.stream(searchProducts({ keyword: "lamp" }))) {
  // 여기서 pool: total=1, idle=0
  break;
}
// break 후 pool: total=1, idle=1
```

`break`는 async generator의 `return()`을 호출하고, SQLBraid의 stream 함수는 `finally` 블록에서 정리를 시작합니다.[^stream]

```ts
} finally {
  // Iterator cleanup runs before lease release so driver cursors/portals still have their owning connection.
  if (iterator?.return) {
    try {
      await physicalContext.run(activeContext, () => iterator!.return!());
    } catch (error) {
      streamError = streamFailed
        ? new AggregateError([streamError, error], "Stream iterator cleanup failed.", { cause: streamError })
        : error;
      streamFailed = true;
      poison(use!.physicalState, streamError);
    }
  }
  ...
  await use!.release(isPoisoned(use!.physicalState));
```

순서가 중요합니다. driver iterator의 `return()`이 먼저 cursor를 닫고, 그다음에 lease를 반환합니다. 반대로 lease를 먼저 반환하면 다른 요청이 그 연결을 가져간 상태에서 이전 cursor의 정리가 같은 연결에 끼어들 수 있습니다.

실패를 다루는 원칙도 이 코드에 있습니다. 행을 읽다가 실패한 뒤 정리까지 실패하면, 두 오류를 `AggregateError`로 묶고 `cause`에는 원래 실패를 둡니다. 정리 오류가 원래 오류를 덮지 않습니다. 정리에 실패한 연결은 poisoned로 표시되고, `release()`에 discard 플래그가 전달됩니다. 저장소에는 early return 때 native resource가 pool lease보다 먼저 닫히는지, 정리 실패 시 lease가 discard되는지를 확인하는 테스트가 따로 있습니다.

### 열린 stream과 트랜잭션 전환은 함께 갈 수 없다

트랜잭션 안의 stream은 트랜잭션 연결을 씁니다. cursor가 열린 상태로 같은 연결에 savepoint를 만들면, driver마다 열린 cursor와 savepoint의 관계가 다르거나 정의돼 있지 않습니다. SQLBraid는 이 조합을 거부합니다.

```ts
await db.tx(async (tx) => {
  for await (const _ of tx.stream(searchProducts({}))) {
    await tx.tx(async () => {});
    // BRAID_STREAM_SCOPE: Close the pinned stream before opening a transaction or savepoint.
  }
});
```

stream을 닫지 않은 채 `tx`나 `session` callback이 끝나도 SQLBraid는 남은 stream을 닫은 뒤 `BRAID_STREAM_SCOPE`로 실패시킵니다.

streaming을 지원하지 않는 adapter에서 결과를 다 읽은 뒤 stream처럼 돌려주는 방법도 있습니다. 그러면 호출하는 코드는 그대로 동작하지만, 메모리를 행 수만큼 쓰지 않는다는 `stream()`의 전제가 깨집니다. 예를 들어 libSQL adapter는 streaming을 지원하지 않아서 `db.stream()`을 `BRAID_STREAM_UNSUPPORTED`로 거부합니다.

## 공통 API가 동일한 native 기능을 뜻하지는 않는다

앞의 stream 거부는 SQLBraid 전체에 적용되는 규칙입니다. adapter가 어떤 기능을 물리적으로 제공하지 못하면 buffering, 흉내, 기능 축소 없이 명시적인 오류로 실패합니다. 취소 신호를 지원하지 않는 driver에 활성 `AbortSignal`을 주면 I/O 전에 `BRAID_CANCEL_UNSUPPORTED`로 실패하고, savepoint가 없는 resource에서 nested `tx`를 부르면 `BRAID_TX_UNSUPPORTED`로 실패합니다. 지원 여부는 [DB·driver·runtime 조합별 지원 매트릭스](https://clickin.github.io/SQLBraid/latest/reference/support/)에 기록합니다.

지금까지 따라온 경로를 책임별로 다시 나누면 이렇습니다.

| 경로상 위치 | 책임 | 지키는 규칙 |
|---|---|---|
| `sql` tag, `render()` | authoring/template | 보간은 값, 구조는 helper, segment = parameter + 1 |
| `StatementBindingAdapter.describe()` | binding/adapter | placeholder·transport는 adapter 소유, 연결 전에 순수하게 실행 |
| lease 획득·반환, `session`/`tx`/`stream` | lifecycle/runtime | materialize 후 mapping 전 반환, tx는 연결 고정, stream은 정리 후 반환, 불확실한 연결은 버림 |
| executor의 결과 정규화 | adapter + TypePolicy | exact 값은 driver 단계에서 문자열로 |
| Standard Schema | application mapping | 연결을 쥐지 않고 애플리케이션 타입으로 변환 |

compiler, metadata, codegen, LSP는 이 표에 없습니다. 런타임은 이 패키지들에 의존하지 않습니다. compiler는 위에서 본 directive lowering을 빌드 단계에서 할 뿐이고, metadata와 codegen은 DB에서 읽은 테이블 정보를 TypeScript 모델로 만드는 선택 도구입니다. 실행 경로의 규칙은 이 도구들이 없어도 똑같이 지켜져야 합니다.

SQLBraid의 추상화가 DB 사이의 차이를 없애지는 않습니다. 값과 구조를 나누는 규칙, 결과 종류 검사, 연결을 언제 빌리고 반환할지, 불확실한 연결을 버리는 규칙은 모든 adapter가 따르는 공통 규칙으로 만들었습니다. placeholder 문법과 transport, 정확한 값을 얻는 방법, streaming·취소·savepoint 지원 여부는 adapter마다 다르고, SQLBraid는 이 차이를 지원 기록과 명시적인 오류로 드러냅니다. 두 번째 묶음을 첫 번째처럼 보이게 만들 수도 있었지만, 그러면 PostgreSQL의 COMMIT 응답이나 열린 cursor처럼 이 글에서 본 문제를 사용자가 알아챌 방법이 사라집니다.
